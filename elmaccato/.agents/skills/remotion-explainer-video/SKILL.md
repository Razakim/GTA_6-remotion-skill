# Elmaccato GTA VI explainers

Every video made in `elmaccato/` explains GTA VI and shares one visual identity through the palette, type, source attribution and editorial tone in `src/da/tokens.ts`. The dark plum Vice City stage, the reviewed Vice City artwork, warm evidence paper, neon frames and GTA-like HUD marks are available tools. Select the stage and tools per beat; the artwork does not need to sit behind every shot. Keep the identity consistent while varying compositions and motion to fit each script. Do not make every video look like the same template.

The project already has its Remotion composition and animation engine in `src/`. Extend that engine when a script calls for a useful new visual idea; do not copy the files under this skill into the application or force an existing block onto an unsuitable beat.

## Turn a script into scenes

1. Start or keep `npm run dev` running and open the current Studio preview before editing the scene plan. Read the whole script first. Preserve its claims and intent; identify the beats, evidence, people, places, contrasts, reveals and emotional turns. Ask for missing source material only when it prevents a factual or visual choice.
2. Refresh the asset index when assets may have changed: `npm run catalog:assets`. Use `public/assets/catalog/media.json` to find candidates by subject and tags, and select only entries whose `availability` is `available`. The catalog paths are relative to `public/` and are ready for Remotion's `staticFile()`; audio/video durations are indexed when `ffprobe` can read the file.
3. If a reference video is supplied, inspect its full duration at regular intervals to find its visual systems and pacing; revisit representative transitions and detailed action at shorter intervals. Write down the sequence of visual ideas, what changes state, what remains anchored, and how graphics relate to the source footage. Use [the animation grammar study](../../../src/motion/animation-grammar.md) as a method guide, not as a mandatory style sheet.
4. Inspect shortlisted assets in context before choosing them. For many candidates, make a contact sheet with `npm run contact:assets -- --subject jason` or `--tag map`. For video sources, extract representative frames with `.agents/skills/remotion-explainer-video/scripts/extract_frames.sh`. Confirm actual content and motion, not just the filename. Annotate useful assets in `media.json` with concise descriptions, tags, mood and framing.
5. For each narrative beat, choose evidence and a visual model that fits its logic: gameplay, a tracked detail, map/route, state meter, inventory, comparison, evidence board, interface, timeline, character profile or an original metaphor. Do not force every beat into cards or a branded frame. Avoid invented evidence, irrelevant filler and repeating the same visual grammar in adjacent scenes. If the library lacks an honest source, make the missing information explicit through a purposeful graphic or report what is unavailable.
6. Match timing to the voice. When voice audio exists, measure its duration and align state changes to audible words or pauses. When there is only text, estimate natural spoken duration and leave breathing room; do not compress a long script into a short montage without stating that it is a summary.
7. Plan a causal sequence for complex beats: what the viewer sees first, what is detected, how the state changes, what consequence follows, and what evidence proves it. Identify moving relationships (a marker follows a person, a route originates at a character, a meter rises with an action, a card transforms into source footage). Decide what should move, what should remain still, and when the composition hands off to another visual model.
8. Use `visual.type: "motion"` for a bespoke composition with independently timed footage, cards, labels, shapes, diagrams, routes and interface layers. Author the layers and keyframes from the current script beat; use groups to keep related objects together. The canvas supports camera movement inside a fixed media crop, changing colors, drawn SVG paths, perspective, position, size, rotation, scale and opacity. See `src/motion/README.md`, the complete reference inventory and the smaller recipe example. Use regular image/video/montage types when they communicate more clearly. A fan, split screen, card row, map, gauge, full-frame moving shot or invented diagram is a choice for that beat, not a recurring quota.
9. Check source alignment for markers and connectors at the actual frames. Tracking is manually keyframed; the engine does not automatically identify or follow objects. Keep text short, legible and subordinate to the evidence. Give maps, state meters and multi-step diagrams enough time to register.
10. Validate the plan with `npm run validate:scenes`, run lint/type checking, and review representative motion at the beginning, middle and end of complex scenes in Studio. Check factual correspondence, media crop, overlapping layers, source transitions, legibility and state continuity. Fix issues before export.
11. When the user asks you to make/create a video, render `GTA6Explainer` to `out/<video-slug>.mp4` after review. Use lower concurrency on constrained machines. Do not render a final video for preview, storyboard or code-only requests.
9. Validate the scene plan with `npm run validate:scenes` and review the Studio preview for pacing, visual continuity, cropping, legibility, audio and factual correspondence. Fix issues before export.
10. When the user asks you to make/create a video, that authorizes producing the finished MP4: render `GTA6Explainer` to `out/<video-slug>.mp4` after review. Use a lower concurrency on constrained machines. If the user asks for a preview, storyboard, or code change only, do not render a final MP4.

## Scene engine and visual choices

Read [the scene schema](references/scenes-schema.md) for the supported data shape. The small visual types serve direct shots, pauses and simple comparisons. `motion` is the authored layer compositor for custom choreography. Its keyframes are deterministic and can animate independent positions, dimensions, rotations, opacity, blur, internal media crop, path drawing and colors. The intended creative unit is a designed beat with a visual model and readable state changes, not an animation preset. Add reusable primitives when they unlock future scenes; keep the composition and choreography specific to the current story.

All motion must be deterministic from `useCurrentFrame()` so Studio previews and rendered frames match. CSS animation classes, wall-clock transitions, and interactive scroll effects from UI libraries are not directly suitable for rendered video. Animation references such as Animata may inspire a card or wipe, but reimplement the chosen idea with frame-based Remotion values and project tokens; do not add a UI animation dependency solely for a scene.

Do not confuse the scene planner with a black-box script parser: the agent interprets each supplied script and writes its visual plan into `src/data/scenes.json`; Remotion then plays and renders that plan. Keep the current script plan in `src/data/scenes.json`; save ordinary scene examples in `src/data/scenes.example.json` and complex motion recipes in `src/data/motion-recipes.example.json`.

## Remotion guidance

This is the project's creative direction, not a replacement for Remotion's technical guidance. Follow the installed Remotion base skills for component structure, media APIs, Studio, captions, maps, licensing and rendering. In particular, read the relevant guidance under `.agents/skills/remotion-best-practices/` when extending the engine; use the dedicated captions, maps or license skills when those features apply. The user's standing request for a finished MP4 when they ask to create a video takes precedence over the base skill's default of not exporting without an explicit request.
